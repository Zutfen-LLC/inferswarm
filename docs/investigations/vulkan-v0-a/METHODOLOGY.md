## Probe

llama.cpp @ commit `8ea290247c87ced2ab245b056ffe96dbcf90d36c`
(ggml-org/llama.cpp master, cloned anonymously over HTTPS; no submodules
at this commit). One commit for every backend/device pair.

Builds (both `-DCMAKE_BUILD_TYPE=Release`, gcc 14.2.0-19, glibc 2.41-12,
cmake 3.31.6, ninja 1.12.1):

- `build-vulkan`: `-DGGML_VULKAN=ON` only (no CUDA) — backend-neutral
  binary; used for BOTH AMD cards AND the NVIDIA Vulkan arm so the CUDA
  backend cannot influence Vulkan-arm codegen.
- `build-cuda`: `-DGGML_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=86`
  (sm_86 = GA104), nvcc CUDA 13.1 V13.1.115 — used ONLY for the NVIDIA
  CUDA arm.

Binary + backend-library SHA-256 hashes retained in
`probe/build-identities.json` (generated by `probe/freeze.sh` on the
host). Exact cmake invocations retained verbatim.

Device-selection proof: every canonical run pins
`--device Vulkan1|Vulkan2|Vulkan3|CUDA0` and retains the tool's own
device-enumeration banner (ggml_vulkan / ggml_cuda lines) plus the
offload summary (`offloaded X/Y layers to GPU`) from stderr. A run whose
banner does not show the intended physical device is discarded.

## AMD native path (HIP/ROCm)

Probed mechanically before any benchmarking: Debian trixie's packaged HIP
stack (hipcc 5.7.1, libamdhip64 5.7.1, HSA runtime 6.1.2, rocm-device-libs
6.0, comgr 6.0) compiles gfx803 code but exposes zero ROCm-capable GPU
devices: `rocminfo` lists only the CPU agent; a minimal HIP program
returns `hipGetDeviceCount` = error 100 "no ROCm-capable device is
detected" under HIP_PLATFORM=amd, with both Polaris cards bound to amdgpu.
Evidence: `inventory/amd-native-path/`. Polaris (gfx803) is not a
supported target of the packaged ROCm runtime. Installing upstream ROCm
for gfx803 would be a scope-expanding intervention on a known-good
baseline, so the AMD native arm is recorded as
`NATIVE_BACKEND_UNAVAILABLE` (mechanically demonstrated, not assumed).
The AMD comparison is therefore Vulkan-characterization-only; no same-device
Vulkan/HIP ratio is computed.

## Model/workload subject (frozen)

- Repository: huggingface.co/bartowski/Qwen2.5-3B-Instruct-GGUF
  (replicable source; anonymous HTTPS download).
- File: `Qwen2.5-3B-Instruct-Q4_K_M.gguf`, 1,929,903,264 bytes.
- SHA-256: `9c9f56a391a3abbd5b89d0245bf6106081bcc3173119d4229235dd9d23253f94`.
- Architecture Qwen2 (36 layers), ~3B params, quant Q4_K_M, ftype Q4_K-Medium.
- Fits fully (weights + KV) in 8 GiB VRAM on every selected GPU with
  `-ngl 99` (all layers offloaded) — no host-offload confound.
- One representation for every device/backend; bytes never change.

Correctness fixture (Phase 3): greedy, deterministic —

```
prompt   : "The quick brown fox jumps over the lazy dog. Explain what happens next in one sentence:"
sampling : --temp 0 --seed 42, -n 48, single-turn
```

Repeated ≥3x on AMD-A, ≥1x on AMD-B and NV-A per backend. Exact stdout
retained per run; generation text compared byte-wise (spinner/control
characters stripped). Logits-level capture: llama.cpp does not expose
logits via CLI without changing execution; numerical observables are the
greedy token streams themselves. Cross-backend semantic equality is
reported; bit-level logit equality is explicitly NOT claimed.

## Performance campaign (Phase 4)

Canonical tool: `llama-bench` (and `llama-cli` for startup/materialization
timing), one physical GPU at a time, `-ngl 99`, one `--device` pinned per
run. Frozen parameters, identical inside every same-device pair:

```
llama-bench -m <subject> -ngl 99 -fa 0 -p 512 -n 128 -r 5 -w 3 --device <D>
```

(prefill 512 prompt tokens, decode 128 tokens, 5 measured reps after 3
warmups; medians + full per-rep rows retained; no best-run promotion.)

Startup/materialization: timed `llama-cli` load-only invocations
(`-n 0`, same -ngl/--device), wall time by `/usr/bin/time`, peak/final
GPU memory by device-appropriate counters (nvidia-smi for NV-A;
amdgpu `mem_info_vram_{used,total}` sysfs polling for AMD), host peak RSS
(`VmHWM`) and post-load `VmRSS` from /proc.

Every retained number carries a BENCHMARKING.md label (MEASURED or
CALCULATED). Ratios are CALCULATED from retained MEASURED medians.
AMD-vs-NVIDIA ratios are never presented as backend ratios.

## Backend capability records

Phase 5 emits one machine-readable record per (physical GPU, backend)
under `capabilities/`: physical identity (PCI IDs/BDF/VRAM independent
of backend), memory resource, backend kind/version/driver, advertised
capabilities (fp16/bf16/int-dot/coopmat/subgroup from the tool banner +
vulkaninfo JSON), correctness result, materialization observations,
prefill/decode metrics, timestamp, limitations. Research evidence shape —
"Compute Unit X supports backend B with evidence E" — NOT a production
resource schema.

## Non-claims

- No claim that Vulkan/HIP/CUDA is "the Compute Unit identity".
- No new heterogeneous numerical threshold is set.
- No InferSwarm planner/Fabric Doctrine/runtime change; no accepted
  #117/#133/#137 evidence touched.
- AMD-native numbers do not exist in this campaign; NATIVE_BACKEND_UNAVAILABLE
  is the truthful record for the HIP arm.
- llama-server is not characterized in V0-A.
- Multi-GPU llama.cpp performance is not used for any verdict.
